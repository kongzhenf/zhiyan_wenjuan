## FR-022: 发布问卷（含截止时间、最大回收数、设备限制配置）

### TC-PB-001: 发布问卷 - 携带全部可选参数成功发布

- **关联需求**: FR-022
- **前置条件**:
  1. 已登录管理员账号获取有效 accessToken
  2. 已创建一份状态为 draft 的问卷（记录问卷ID为 `{qid}`），且该问卷至少包含一道配置完整的题目
- **测试步骤**:
  1. 发送请求:
     ```
     POST http://10.32.129.153:8082/api/questionnaires/{qid}/publish
     Header: Authorization: Bearer {accessToken}
     Header: Content-Type: application/json
     Body: {
       "deadline": "2026-12-31 23:59:59",
       "maxResponses": 1000,
       "allowDuplicateDevice": false
     }
     ```
  2. 验证响应状态码和响应体
  3. 发送查询请求确认问卷状态:
     ```
     GET http://10.32.129.153:8082/api/questionnaires/{qid}
     Header: Authorization: Bearer {accessToken}
     ```
- **预期结果**:
  1. 步骤1返回 HTTP 200
  2. 响应体中 `code` 为 200（或成功标识），问卷状态变更为 `active`
  3. 响应体中应包含 `accessCode` 字段（非空字符串，用于唯一访问标识）
  4. 步骤3查询结果确认: `status` = `active`，`deadline` = `2026-12-31 23:59:59`，`maxResponses` = 1000，`restrictDevice` = true（即不允许重复设备提交）
- **优先级**: P0
- **测试类型**: 正常流程

## 设计决策记录

1. **HTTP状态码判定**: 接口定义未明确指定业务错误对应的HTTP状态码，用例中统一假设业务校验失败返回 HTTP 400，实际测试时需根据系统实现调整。
2. **响应体结构假设**: 假设API响应遵循 `{"code": xxx, "message": "...", "data": {...}}` 的通用格式，错误码字段为 `code`。
3. **TC-PB-005 补充覆盖**: FR-022 要求最少4条用例，除正常流程3条外，增加了 closed 状态不可发布的反向验证（TC-PB-005），确保不可逆状态流转得到覆盖。
4. **TC-PB-014 补充覆盖**: FR-026 要求最少2条用例，额外增加了指定 size 参数的正常流程用例（TC-PB-014），覆盖可选参数的有效性验证。
5. **设备限制字段映射**: 请求体中 `allowDuplicateDevice: false` 对应数据库字段 `restrict_device: true`（语义取反），用例验证时需注意此映射关系。
